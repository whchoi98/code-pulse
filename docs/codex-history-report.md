## 공식 RSS의 범위

현재 설정된 주소는 `https://developers.openai.com/codex/changelog/rss.xml`이며 308 응답으로 `https://learn.chatgpt.com/docs/changelog/rss.xml`에 이동한다.

직접 다시 읽은 응답은 저장된 `codexRss.txt`와 바이트까지 같았다.

- 크기: 149,000바이트
- SHA-256: `1e51a944f299bfc511f8078937e813b358bdafe175f9ea4bb5ce49ae66699fb7`
- Last-Modified: 2026-10-07 21:22:37 GMT
- 전체 항목: 121개
- 전체 날짜 범위: 2025-05-19부터 2026-10-07까지
- 2026년 범위: 원본 102개, 현재 Codex 키워드 필터 기준 94개
- 올해 첫 제품 소식: 2026-01-14
- 현재 파서의 CLI 제목 조건에 해당하는 버전별 안정판: 0개

RSS는 연초보다 오래된 제품 소식을 포함한다. 현재 공개된 제품 변경 기록의 연초 범위를 확보하기 위해 별도 RSS 페이지나 아카이브를 요청할 필요는 없다. `atom:link`에는 `self`만 있고 다음 페이지 링크는 없다. 저장된 공식 HTML에도 RSS의 121개 항목 주소에 해당하는 앵커가 모두 있었다.

이 RSS는 ChatGPT와 Codex의 혼합 피드다. Codex 관련성 판별은 날짜 범위와 별도로 필요하다. 버전별 CLI 안정판 기록은 RSS만으로 대체할 수 없다.

## GitHub 페이지 범위와 응답 크기

REST 첫 페이지는 `https://api.github.com/repos/openai/codex/releases?per_page=20`이다. 확인한 `Link` 헤더의 마지막 페이지는 61이었다. 연초가 걸친 구간은 REST 20개 기준 약 43페이지이며, 다음 44페이지는 HTML의 추가 확인 구간에 해당한다.

REST 첫 페이지의 원문은 6,037,519바이트였다. 전체 API 순회는 큰 `assets` 메타데이터를 반복해서 가져오며, 익명 API의 시간당 요청 한도도 고려해야 한다. `Link` 헤더는 `/repositories/965415649/releases` 형태를 사용하므로 현재 `/repos/openai/codex/releases` 허용 경로와도 다르다.

HTML 경로는 `https://github.com/openai/codex/releases?page=N`이며 페이지마다 10개를 담는다. 다음 페이지는 실제 `rel="next"` 링크로 확인한다.

| 84 | 2026-01-08부터 01-13 |
| 85 | 첫 올해 안정판 0.78.0과 0.79.0, 2026-01-05부터 01-07 |

발표 시각은 목록 안에서 완전한 내림차순이 아니다. 첫 과거 항목에서 종료하지 않고 페이지 전체를 읽으며, 시험판의 발표 시각까지 포함해 연속 두 페이지가 모두 하한 이전일 때 종료한다. 날짜 범위를 확인하지 못한 채 웹의 100페이지 한도에 도달하면 실패한다.

목록 원문 총량은 40,977,248바이트이며 가장 큰 페이지는 706,435바이트다. 실제 순회에서 250ms 간격은 42페이지에서 HTTP 429를 일으켰다. 어댑터는 같은 GitHub 호스트의 모든 HTML 요청 사이에 2초를 둔다. 오류 처리는 전달받은 `fetchDocument`와 상위 수집기의 재시도 정책을 사용하며, 최종 실패를 부분 성공으로 바꾸지 않는다.

## 목록의 본문 잘림과 개별 페이지 보강

GitHub 목록은 긴 Markdown을 약 10,000자에서 자른다. 잘린 `.markdown-body` 바로 뒤에는 실제 `Read more` 링크가 있다. 첨부 파일 목록의 `expanded_assets`와는 별개다.

0.161.0의 목록에는 New Features, Bug Fixes, Documentation, Chores 요약이 남아 있었지만 뒤쪽 Changelog의 PR 번호 46개가 빠져 있었다. 개별 릴리스 페이지에서 해당 내용이 모두 확인됐다. 0.143.0도 목록의 렌더링 텍스트 9,670자에 비해 개별 페이지는 20,328자였다.

API가 이미 제공한 버전은 API 원문과 발표 시각을 유지한다. 과거 안정판 중 명시적 `Read more`가 있는 29개만 공식 `/releases/tag/...` HTML을 추가로 읽는다. 상세가 없거나 다시 잘려 있으면 실패하며, 목록의 짧은 본문을 완전한 결과로 반환하지 않는다.

추가 HTML 총량은 10,791,670바이트, 최대 파일은 575,419바이트다. 전체 원문 118개는 합계 57,806,437바이트이며 각 응답은 8MiB, 즉 8,388,608바이트 제한 안에 있다. 원문을 하나의 거대한 응답으로 합치지 않는다. 첨부 파일과 `expanded_assets`는 요청하지 않는다.

0.156.0의 후보 본문은 블록 사이 줄바꿈을 포함해 43,102자다. 전체 HTML을 가져온 뒤 다시 30,000자로 자르지 않도록 역사 어댑터의 추가 절단을 없앴다. 최신 API는 기존 API 파서의 원문 처리 기준을 유지한다.

## 검증과 우선순위

- API가 알고 있는 모든 태그를 HTML 대체 대상에서 제외한다. 최신 API가 초안이나 시험판으로 판정한 태그를 오래된 stable HTML로 되살리지 않는다.
- 본문이 있는 API 안정판은 하한 이전이어도 후보로 유지한다. 최종 기간 필터와 다른 피드의 날짜 보정은 엔진이 담당한다.
- HTML의 `released this` 설명에 연결된 `relative-time[datetime]`만 발표 시각으로 사용한다. 커밋 시각, 첨부 파일 시각이나 날짜만 있는 값을 대신 쓰지 않는다.
- 상세 HTML의 `og:url` 또는 canonical 주소를 요청한 태그와 먼저 대조한다. 선언이 없거나 다른 버전의 주소가 있으면 본문과 날짜를 합치기 전에 실패한다.
- 다음 페이지의 저장소, 경로와 증가하는 페이지 번호를 검증한다. 반복되는 페이지 내용과 불명확한 종료 표시도 실패한다.
- 반환된 원문마다 `onDocument`를 호출하며 callback 실패를 삼키지 않는다.

전용 테스트에서는 초기 15개 실패를 확인한 뒤 구현했다. Read more, 30,000자 이후 본문, SDK 채널, 잘못된 상세 버전과 최신 API 공개 유형 우선 문제도 각각 실패를 재현하고 수정했다.

최종 Node 22 검증에서 `npm test -- tests/codex-history.test.ts`의 28개 테스트가 26.47초에 통과했다. 어댑터와 전용 테스트를 대상으로 실행한 엄격한 TypeScript 검사도 종료 코드 0을 확인했다.

정상 재생은 API 1개, 목록 88개, 상세 29개를 읽고 `onDocument`를 118회 호출했다. 결과는 고유 안정판 105개로 CLI 104개와 SDK 제품 기록 1개다. 최초와 최신 발표 시각, 최신 API 원문 일치와 긴 과거 본문 보존을 확인했다.

별도 재생에서는 실제 0.157.0 상세 본문을 0.158.0 응답으로 바꿔 넣었을 때 식별 주소 불일치로 거부했다. 최신 API의 0.161.0을 시험판으로 바꾸면 오래된 HTML이 있어도 해당 버전이 제외되는지도 확인했다.

재생 중 네트워크를 차단했고 저장된 원문의 SHA-256을 모두 확인했다. 대기 타이머만 별도 검증 프로세스 안에서 가속했다. 실제 운영 어댑터의 2초 간격은 유지한다.
